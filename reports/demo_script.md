# 면접 시연 시나리오 (3~4분)

시연 수단은 세 가지이고 준비 상황에 따라 고른다. 어느 경우든 화면 구성은 같다(검사 이미지 + 탐지기 점수·단계 + Ours / B1 / 정답).

| 수단 | 명령 | 필요한 것 | 장점 / 한계 |
|---|---|---|---|
| A. FastAPI 캐시 모드 | `python -m app.api --open` | 프로젝트 폴더 + 데이터셋 5.8GB + 이미지 캐시 2.0GB + 탐지기 캐시 0.7GB + SFT 기록·예측 60MB (합계 약 8.6GB), Python 3.11, `pip install -r requirements.txt`. GPU 불필요 | 이미지 1,568장을 자유롭게 넘기며 설명. 인터넷 불필요 |
| B. FastAPI 라이브 모드 | `python -m app.api --live --open` | A + RTX 3060급 GPU(VRAM 6GB) + Qwen3-VL-4B 가중치(약 8GB, Hugging Face 캐시) + 어댑터 `runs/m2_4b_f{0,1}_s0/final` (각 138MB) | 버튼 한 번으로 실제 생성(배치 1 기준 약 10~20초, 첫 호출은 어댑터 적재 1~2분). GPU PC에서만 |
| C. 영상 | `reports/figures/demo.mp4` (약 1분, 소리 없음, 자막 띠) | 재생기만 | 어떤 환경에서도 재생. 상호작용 없음 |

권장: A를 노트북에 준비해 두고 C를 보험으로 가져간다. B는 GPU PC를 원격으로 보여 줄 수 있을 때만 쓴다.
서버가 뜨면 `http://127.0.0.1:8008/`이 화면, `/docs`가 API 문서(FastAPI 자동 생성)다. `?id=<image_id>`로 특정 이미지를 바로 연다.

## 흐름과 말할 요점

1. 첫 화면(30초). 제목과 상단 칩을 가리키며 문제와 구조를 말한다.
   "조립·포장 검사에서 긁힘 같은 구조 결함뿐 아니라 부품 누락·수량 같은 논리 결함을 잡고, 왜 이상인지와 조치를 두 줄로 내는 시스템입니다.
   1차는 비지도 탐지기 SALAD(image AUROC 96.1, 111ms), 2차는 12GB GPU에서 QLoRA로 적응시킨 Qwen3-VL-4B입니다.
   탐지기 점수에 따라 통과·판정·설명 세 구간으로 나눠 VLM 호출을 이미지의 약 23%로 줄였습니다."
2. 성공 사례(40초). 라벨 '논리 이상', 푸시핀 `pushpins/test/logical_anomalies/001` (`?id=`로 바로 열기).
   단계 띠가 '설명 구간'에 켜진 것, VLM 입력 3장(검사·탐지기 crop·정상 참조), Ours의 두 줄 출력과 '그룹 정답' 배지를 짚는다.
   "출력은 고정 서식이고 Guard가 결함 그룹·위치 표현을 KB와 대조해 형식 준수 99.9%입니다."
3. 정상 통과(20초). 라벨 '정상'으로 바꿔 '○' 표시 이미지 하나. 단계 '통과', 출력 없음이 정답.
   "같은 재현율 목표에서 탐지기 단독보다 오경보를 65% 줄였습니다. 대신 재현율 4%p를 잃었고, 이 손익은 공정의 놓침 비용에 따라 임계값으로 조정합니다."
4. 실패 사례(40초). `breakfast_box/test/logical_anomalies/055` (수량 결함을 다른 그룹으로). B1 칸이 정답이고 Ours가 오답인 것을 그대로 보여 준다.
   "같은 입력을 쓰는 단순 분류기 B1이 그룹 정확도 67.0으로 VLM 55.7보다 높습니다. 가설과 반대였고 숨기지 않았습니다.
   원인을 분해해 보니 개수 계열 결함은 같고 장면 전체의 구성 결함에서 격차가 났습니다. 8B, 라벨 수, 입력 표현 실험으로 용량·데이터 부족은 원인이 아님을 확인했습니다."
5. 결과 요약(40초). 상단 칩의 Ours/B1/P3 수치.
   "B1의 판정을 프롬프트에 넣으면 4B가 B1을 3.1%p 넘지만 출력의 77%가 힌트를 그대로 따른 것이라 VLM 단독 개선으로 보지 않습니다.
   실용 구성은 판정은 분류기, 설명·검증은 VLM인 계층이고, 그 구성으로 검사원 보조에 쓸 수 있습니다."
6. (B일 때) 실시간 생성 버튼(30초). 생성 시간과 Guard 단계가 함께 나온다. 캐시 결과와 다르면 greedy 생성이라도 양자화·커널 차이로 토큰이 달라질 수 있다고 말한다.
   시간은 배치 1에서 장당 약 10~20초다(표1의 6.1초/장은 학습 프로세스 안 배치 2 처리량). 같은 어댑터를 bf16 기반 모델에 올려도
   빨라지지 않고 VRAM 11.4GB를 쓴다(`reports/ops/gen_probe_demo4b_*.json`). 시연 중에는 다른 GPU 사용 앱을 닫는다.

## 예상 질문과 짧은 답

- 왜 VLM이 분류기에 지는가. 이 데이터 규모(fold당 이상 약 420장)에서 VLM은 장면 전체의 구성 정보를 스스로 뽑지 못한다. SALAD 구성 점수를 글로 줘도(P3 변형 A) 효과가 없었고, 분류기의 판정을 주면 받아 적었다.
- 그래도 VLM을 쓰는 이유. 설명과 조치 문장을 고정 서식으로 내는 역할은 분류기가 못 한다. 판정 책임은 분류기와 사람에게 두고 VLM은 설명 계층으로 둔다.
- 현장 적용 가능성. 탐지기는 시범 적용 가능, 진단 자동 결정은 불가. 낮은 FPR 운영점 평가, 조명·카메라 드리프트 시험, 실제 결함 검증 분할, 설명의 사실 오류율 측정이 선행 과제다.
- 재현성. 예측 원본·점수 캐시·어댑터 카드를 공개했고 `publish_predictions restore` 뒤 표 5개가 CI에서 바이트 단위로 재계산된다.
- 왜 한국어 고정 서식인가. 현장 작업자가 읽을 리포트이고, 서식이 고정돼야 KB 대조와 자동 채점이 가능하다.
- 라이선스. 데이터셋 CC BY-NC-SA 4.0을 승계해 어댑터도 비상업·동일 조건. 화면과 영상의 이미지도 같은 조건이라 외부 게시는 하지 않는다.

## 문제가 생겼을 때

- 포트 충돌: `python -m app.api --port 8010 --open`.
- 라이브 생성 실패(VRAM 부족, 가중치 없음): 서버를 캐시 모드로 다시 띄운다. 화면은 같다.
- 화면이 비어 있음: 상단 경고 띠의 메시지를 본다. 대개 `data/sft/m2_salad_f*/heldout.jsonl` 또는 `data/vlm_cache`가 없는 경우다.
- 아무것도 안 될 때: `reports/figures/demo.mp4`를 재생하고 위 흐름대로 말한다.

## 영상 다시 만들기

`python -m app.record_video` (Edge 헤드리스 + CDP, 약 2분). 사례는 그림 4와 같은 규칙으로 고른 성공 3·정상 1·실패 3이고
`--hold`로 사례당 표시 시간을 바꾼다. GIF는 `python -m app.record_gif`.
